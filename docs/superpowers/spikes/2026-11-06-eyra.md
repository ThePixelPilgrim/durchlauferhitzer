# Eyra spike — can a pure-Rust libc replace glibc/musl?

2026-11-06, throwaway spike on `main` at `9935fae`, x86_64, kernel 6.18, run as root. Nothing was committed.

**Recommendation: no, revisit later.** The server does build and run on Eyra: every server test passes, including under `seccomp_action kill`. But getting there meant going around Eyra for about 20 system calls, and Eyra needs an old pinned nightly to build at all. It adds 35 crates with a single maintainer. It also execs the system's C `getent` to look up a user. Most of the work of adopting it would be our own raw system-call layer. A layer like that is worth building only once the owner wants it anyway.

## 2. Spike build

Changes made (patch kept outside the repo, 17 files, +469/−62):

- **Dependency:** `driver/Cargo.toml` takes `eyra` (renamed `std`, feature `experimental-relocate`).
- **Build script:** a new `driver/build.rs` passes `-nostartfiles`.
- **Toolchain:** `rust-toolchain.toml` set to `nightly-2026-02-20`.
- **Static linking:** `.cargo/config.toml` adds `+crt-static`. This replaced the existing musl-target section.
- **Lock file:** `Cargo.lock` gains 37 packages, with `rustix` pinned to 1.1.4.
- **Own system calls:** a new `driver/src/sys/raw.rs` (62 lines) issues raw system calls through `asm!` for x86_64 and aarch64. It also has wrappers for `prctl`, `setsockopt`, `getsockopt` and `fcntl`. About 25 call sites in `sys/` now use it: setuid/setgid/setgroups/setresuid, getresuid/getresgid, `signalfd4`, `readahead`, `personality`, capget/capset, Landlock, seccomp, `openat2`, `fstat`, prctl, get/setsockopt and `fcntl`.
- **Test support:** `driver/tests/support/child.rs` gets the same treatment. std's `Command::uid`/`gid` hits c-scape's `todo!()` in the forked child, so it became our own `pre_exec` hook.
- **Seccomp filter:** the filter changes are listed in section 3.

In short, Eyra did not replace our libc calls. We had to go around it.

Linking:

| Build | Result |
|---|---|
| Default (PIE) | No `NEEDED` entries, but the interpreter is still `/lib64/ld-linux-x86-64.so.2`. glibc's loader does the relocations, so this is still C. |
| `+crt-static` alone | static-pie; the hello world segfaults at start. |
| `+crt-static` and `experimental-relocate` | **static-pie with no `NEEDED`, no interpreter, no libgcc_s.** The linker trace shows only Rust rlibs: no `crt*.o`, no system archives. "Relocate" means Rust code patching itself at startup, which the README calls "outside of any Rust semantics". Non-PIE static (`relocation-model=static`) also works, but loses ASLR. |

Size of the release binary: glibc build 1.12 MB (0.87 MB stripped), Eyra build 1.45 MB (1.11 MB stripped), about **+28%**.

## 3. Runs (driver suite, `DURCHLAUFERHITZER_REQUIRE_ROOT=1`, `TMPDIR=/tmp`)

**Normal and kill-switch runs:** 329 passed and 9 failed, the same in both. **All 9 server-test binaries pass in both modes**: budget, cli, containment, privileges, restart, shutdown, smoke, startup, systemd. The one exception is containment's clock-shim test (below). The release binary under `seccomp_action kill` serves requests and drains on SIGTERM.

The 9 failures are artifacts of Eyra or of the spike, not server bugs:

- **Filter unit tests (6):** they pin the glibc/musl table, which the spike changed.
- **`unsafe_confined`:** it caught the spike's own `unsafe` in the test support.
- **`the_clock_system_call_passes_the_filter_under_kill`:** `LD_PRELOAD` cannot load into a static binary. The vDSO fallback stays untested.
- **`seccomp_self`:** `rustix` debug-asserts that `getppid` cannot fail, so a filtered "infallible" call panics in debug builds.
- **`free_port` fork race:** c-scape `close(EBADF)` hits a `rustix` debug assertion in the forked child.
- **`seccomp_program` threads:** a thread started after the filter is refused. Eyra's `clone` adds `CLONE_CHILD_SETTID` to glibc's flags, which `Rule::Thread` does not allow, so the result is SIGSYS. The server never starts threads after the filter.

**System calls after the filter** (`strace -f` over the 9 server tests), compared with today's glibc table:

| Needed under Eyra | Instead of | Already accepted under FR-PROC-06? |
|---|---|---|
| `epoll_pwait` | `epoll_wait` | Yes: the musl x86_64 entry and the aarch64 entry. |
| `ppoll` (rustix polls with `ppoll` on x86_64 too) | `poll` | Yes: the aarch64 entry. |
| shared `FUTEX_WAIT` (origin's join waits on the thread id) | `FUTEX_WAIT_BITSET\|CLOCK_REALTIME` | Yes: the musl entry. |
| `tkill` SIGABRT to the main thread (c-scape `abort`) | `tgkill` | Yes: musl's `AbortMain` rule. |

Not seen: `rseq`, `set_robust_list`, `sched_getaffinity`, `brk`, `mremap`, `madvise`, `clone3`. So the table would get about 7 entries smaller, with no new kind of entry, and every addition is acceptable under FR-PROC-06.

Before the filter fix, two things broke:

- Under `fail`, `epoll_pwait` got EPERM and the event loop exited with status 2.
- origin's join `debug_assert`s on EPERM. The panic inside a no-unwind function ended in `ud2`, so the process died by SIGILL, not SIGABRT.

The log flush was cut short only because `ppoll` got EPERM; it is fine once `ppoll` is listed. An `abort` from a worker thread ends like musl's: `tkill(SIGABRT)` is refused, then `tkill(SIGKILL)` is refused, then `ud2` (SIGILL under `fail`, SIGSYS under `kill`).

**Where our code depends on glibc/musl behaviour:**

- **User lookup works, but by exec'ing the system `getent`.** It needs `getent` on `PATH`, so it is absent from scratch and distroless images. Any `getent` exit status other than 0 or 2 makes c-scape panic, which aborts the process. Startup gains a fork and exec, and NFR-RES-05's NSS note becomes a pipe plus a child process. Parsing `/etc/passwd` ourselves would lose NSS, including systemd `DynamicUser=`, which goes through nss-systemd.
- **Privilege drop:** Eyra has no process-wide setxid broadcast, so the raw calls set the ids of one thread only. That is correct today only because the drop runs while the process has one thread, and that would become a rule we must keep.
- **Clock shim:** the `LD_PRELOAD` test does not apply to a static binary.
- **errno strings:** same text as before; our logs use the decimal errno anyway.
- **Signals:** signalfd, the signal mask, SIGPIPE ignored, TERM/HUP/INT all pass.
- **Abort:** dies by SIGABRT on the main thread, through `tkill`.

**core and sim:** they build and pass on `nightly-2026-02-20`. They do not link Eyra.

## 4. Assessment

**What it would gain:**

- No C in the binary: no glibc, no musl, no libgcc_s.
- One static binary.
- One system-call set, because the glibc and musl tables merge.
- A filter about 7 entries smaller.
- A thread-safe `setenv`.

**What it would cost:**

- **Nightly in the product, pinned to an old date.** Eyra does not build on current nightly or with current `rustix`, so toolchain fixes wait on upstream.
- **Supply chain.** "libc only" becomes 35 new crates, 8 build scripts, prebuilt `.a` blobs, one maintainer, and no `eyra` release since April 2025.
- **`unsafe` moves into dependencies:** about 195k lines that the README itself does not rate above C.
- **We still own a raw system-call module of about 20 calls,** because c-scape's libc layer panics or stubs them.
- **NSS through `getent`,** which is a C binary.
- **Static-PIE needs the experimental self-relocation.**
- **Debug builds panic on filtered "infallible" calls** (rustix debug assertions).
- **Packaging and CI:** the musl/Alpine path is replaced, and a nightly gate would be needed on both architectures. aarch64 was not tried here.

**Revisit when all of these hold:**

1. Eyra or origin build on stable, or at least on current nightly with current `rustix`, and release regularly. A second maintainer or a foundation home would help.
2. c-scape implements setxid broadcast, `setgroups`, generic `syscall`/`prctl`/sockopt/`fcntl`, `signalfd` and `readahead`.
3. Static-PIE relocation is no longer experimental.
4. The owner accepts either `getent` or losing NSS.

Not even as an optional build for now: it would carry a nightly toolchain, its own filter table and the shim, for a configuration nobody ships.
