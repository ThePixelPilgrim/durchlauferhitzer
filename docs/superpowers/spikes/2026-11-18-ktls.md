# kTLS spike — can the kernel carry our TLS records?

2026-11-18, a throwaway spike. The code is on the scratch branch `spike-ktls` at `0fcb392`, which is never to be merged. It ran in GitHub Actions runs 44293493794 and 44294187634. Nothing kTLS can run in the cloud container, because its kernel has `CONFIG_TLS` unset.

**Recommendation: kTLS can carry the design.** TLS 1.3 with ChaCha20-Poly1305 and AES-GCM, and `sendfile` through it, worked on every kernel probed. The handshake records stay in userspace, and the server hands the keys to the kernel only for application data.

## 1. What this means for the design

This is the controller's reading, for the owner to decide; nothing here is decided. The tags give the evidence:

- `(observed)`: the runner probes.
- `(source)`: kernel or distribution source read by the research.
- `(unverified)`: the research says it could not verify it.

1. **Handshake records stay in userspace, so `chacha20poly1305` stays in the product.** Changing the keys on a socket, both from handshake to application keys and on KeyUpdate, works on 7.0 and fails with `EBUSY`(16) on 6.8. By source it arrived in 6.14 and is not in the 6.1, 6.6 or 6.12 stable series. CentOS Stream 10 has it as a backport. `(observed; source)`
2. **The switch to the kernel works if the server reads record-exact.** Bytes queued before `TLS_RX` is installed decrypt fine when the queue starts at a record boundary. A partly read record makes the first `recv` fail with `EMSGSIZE`(90). So the handshake reader reads the 5-byte header, then exactly the record body, and never more. `(observed)`
3. **A client KeyUpdate cannot be honoured on kernels without the key change.** On 6.8 the KeyUpdate arrives as a type-22 record with body `18 00 00 01 00`, and the next record is still read with the old key. A real client's next record uses its new key, which the kernel should reject with `EBADMSG`(74), but that was not probed. The consequence to decide: the server closes such a connection, and never sends a KeyUpdate itself. `(observed; unverified for the new-key record)`
4. **The kernel does not hide keys from the socket's holder.** `getsockopt(SOL_TLS, TLS_TX)` or `TLS_RX` returns the key in clear, with IV, salt and the live sequence number. This does not break the owner's three guarantees, because the server sees the plaintext anyway and the parser never holds the socket. But a second process installing the keys over `SCM_RIGHTS` works and buys no secrecy, so the simpler channel is: the key process hands the traffic secrets to the server, and the server installs them. `(observed; source)`
5. **Loading the `tls` module on demand needs `CAP_NET_ADMIN`.** An unprivileged attach with the module not loaded fails with `ENOENT`(2). On the runners, Azure hosts had the module loaded already and AWS hosts did not, and the same image label landed on either. `--check` and the startup should say which of two ways applies: `(observed; source)`
   - the server attaches the ULP once before the privilege drop, which loads the module;
   - the module is loaded at boot, the only way for a non-root service under systemd socket activation.
6. **The cipher question is open again.** All three ciphers work in kTLS on the kernels probed, but the kernel's TLS option does not select the ChaCha20-Poly1305 cipher. If the research's reading below holds, a ChaCha-only server gets no kTLS on current Alpine, and AES-GCM is a measured need under decision 5(d). The settling check: on an Alpine 3.23 host, `modprobe tls`, then the probe binary or `modinfo chacha20poly1305`. `(observed; source)`
   - Alpine 3.23 and later dropped the config line that 3.22 has. `(unverified on a built kernel)`
   - Flatcar's config never lists it. `(unverified on a built kernel)`
   - RHEL 8 has no ChaCha20 in its kTLS code. `(source)`
7. **The kernel floor by feature is 5.11.** ChaCha20-Poly1305 in kTLS arrived in 5.11, TLS 1.3 in 5.1, and the key change in 6.14. Only 6.8 and 7.0 were probed. The distribution consequences are in the table below. `(source; observed for 6.8 and 7.0)`
8. **Closing a connection is the server's job.** The kernel sends no close_notify, and a truncated record followed by FIN reads as a clean end of stream. A `send` after `shutdown(SHUT_WR)` reports success and the data is lost. See the list below for what the server must do. `(observed)`
9. **`sendfile` and `splice` work unchanged with epoll.** 1 MiB goes out as 64 records of 16384 bytes. Non-blocking `sendfile` returns `EAGAIN`(11) and resumes on `POLLOUT`. On receive, a half-arrived record shows no `POLLIN`, and `recv` returns `EAGAIN`(11). `(observed)`
10. **There is no kTLS on gVisor or on stock Firecracker guest kernels.** This cloud container is such a guest. With "refuse to start without kTLS", TLS is unavailable there, and plain HTTP behind an external terminator remains the answer. An operator's own guest kernel may differ. `(source; observed in this container)`
11. **The kernel attack surface is real.** The research lists 43 CVEs on the software path, 35 of them from 2024 to 2026, and calls the list "most, not all". Once the module is loaded, any process can reach it without privilege; CVE-2023-0461 was exploitable that way. `(source; observed for unprivileged use)`
12. **The seccomp allow-list gains a short kTLS set.** It is listed below, taken from the spike's code, not from strace. `(observed)`

Closing a connection (point 8). The server must:

- send its own close_notify as an alert record (`TLS_SET_RECORD_TYPE` 21), which works (10.4);
- track its own write-side state, because a `send` after `shutdown(SHUT_WR)` returns the full length and vanishes (10.6);
- treat an end of stream without a received close_notify as truncation (9.5);
- close on a received fatal alert, because alerts change no socket state (5.4).

It must not rely on the kernel for any of these.

The seccomp set for the data path (point 12):

- `setsockopt` `SOL_TCP`(6) / `TCP_ULP`(31), value `"tls"`;
- `setsockopt` `SOL_TLS`(282) / `TLS_TX`(1), `TLS_RX`(2);
- optional: `setsockopt` `SOL_TLS` / `TLS_TX_ZEROCOPY_RO`(3), `TLS_RX_EXPECT_NO_PAD`(4);
- `sendmsg` with cmsg `SOL_TLS` / `TLS_SET_RECORD_TYPE`(1);
- `recvmsg` with a control buffer for `TLS_GET_RECORD_TYPE`(2);
- `sendto` and `recvfrom` with `MSG_NOSIGNAL` and `MSG_MORE`;
- `sendfile`, `splice` from a pipe, and `shutdown(SHUT_WR)`.

The server never needs `getsockopt` at `SOL_TLS`, so the filter can refuse it. `TLS_RX_EXPECT_NO_PAD` is the path of CVE-2026-74611, a reason to leave it off.

## 3. Where the probes and the kernel documentation disagree

Four results are not in `Documentation/networking/tls.rst` (master) at all, and they matter for the design.

1. **Keys come back out (8.3).** The documentation only says the options are readable.
2. **A `send` after `shutdown(SHUT_WR)` succeeds and the data vanishes (10.6).** Plain TCP gets `EPIPE`(32).
3. **A key change with an open `MSG_MORE` record re-encrypts it under the new key (6.11, 7.0).** In TLS 1.3 those bytes belong to the old epoch.
4. **A truncated record followed by FIN reads as a clean EOF (9.5).** Truncation detection is left to userspace.

Further points:

- `TLS_TX_ZEROCOPY_RO` is documented "for device offload only", yet software kTLS accepts it, even before `TLS_TX` (4.5 to 4.7). Data stays correct.
- The KeyUpdate pause is triggered by the record content alone (6.12). On 7.0, a type-22 record whose body starts with byte 24 pauses RX even when the peer keeps the old key.
- Confirmed as documented:
  - `sendfile` uses maximum-size records;
  - `EINVAL` for a wrong header version (9.9);
  - `EMSGSIZE` for an oversized record (9.2 to 9.4);
  - `EBADMSG` for a bad tag (9.1) and a wrong sequence number (9.11);
  - a plain `recv` on a control record errors (5.3);
  - `recv` never mixes record types (5.5);
  - `EKEYEXPIRED` and no `poll` input after a KeyUpdate on 7.0 (6.3, 6.4, 6.12);
  - a version or cipher change on a key change is refused (6.8).

## 5. Not settled

- **Alpine 3.23 and later, and Flatcar:** whether ChaCha20-Poly1305 is built at all. Only the missing config line is verified.
- **Kernels between 6.8 and 7.0:** none was probed; 6.14 as the key-change release rests on source.
- **Distribution kernels:** no Alpine, Debian or RHEL kernel was probed.
- **A real TLS client:** none was involved. The probes used fixed test keys with both ends in one process, so interoperability is untested.
- **The new-key record on 6.8:** what a real client's record after its KeyUpdate does on a kernel without the key change.
- **Socket state after `EMSGSIZE` or `EINVAL`** (9.2 to 9.4, 7.2, 9.9): `SO_ERROR` read 0, but the failing `recv` may have cleared it.
- **`TLS_TX_ZEROCOPY_RO`:** only acceptance and data correctness were checked; loopback has no offload.
- **`TlsDecryptRetry`** under `TLS_RX_EXPECT_NO_PAD` with a full-size receive buffer.
- **`ss` and socket-diag** visibility of kTLS state.
- **Distribution configs from memory:** Debian 12 and 13, Arch, Amazon Linux 2023 and Google COS.
- **Newer Ubuntu HWE kernels** (6.11 to 7.0 for 24.04): they exist, but their configs were not read.
- **RHEL minor releases:** only CentOS Stream heads and the 8.8 snapshot were read, not Red Hat's release notes.
- **The research's CVE list:** capped by Ubuntu's search, with no NVD or Debian tracker access.
- **gVisor variants:** Cloud Run gen2 and GKE Sandbox runtimes were not checked.

## 6. Method

The spike was a throwaway binary crate run by a dispatched workflow on GitHub-hosted runners.

- **Code:** `spike/ktls` (one `main.rs` of 1813 lines) and `.github/workflows/spike-ktls.yml`, on `spike-ktls`.
- **Rounds:** round 1 at `ab72871` (run 44293493794), round 2 at `0fcb392` (run 44294187634). All jobs were green.
- **Runner images:** `ubuntu-22.04`, `ubuntu-22.04-arm`, `ubuntu-24.04`, `ubuntu-24.04-arm` and `ubuntu-latest` (26.04).
- **Invocations per job:** as `runner` before `modprobe`, as `runner` after `sudo modprobe tls`, and under `sudo`. Round 2 added a root attach before `modprobe`.
- **Kernels seen:** `6.8.0-1070-azure` (x86_64, aarch64); `7.0.0-1014-aws`, `7.0.0-1016-aws`, `7.0.0-1017-azure` (x86_64, aarch64) and `7.0.0-1019-azure`.

The research read source, not documentation:

- kernel files at each tag from v4.13 to v7.2, fetched from raw.githubusercontent.com;
- distribution configs from Ubuntu's kernel packages, Alpine's aports, the CentOS Stream and Fedora kernel-ark trees, Flatcar's scripts, gVisor and Firecracker;
- CVE records from Ubuntu's CVE search and the CVE project's list.

The proxy refused about 75 hosts: 59 named ones, plus about 15 Debian mirrors and further Alpine mirrors. Among them are git.kernel.org, lore.kernel.org and every Debian source host. GitHub's API and commit pages for the kernel were refused too, so commit hashes are from memory.
