# Stage 7 owner stop: measurement for Tasks 6 (splice) and 7 (threads)

main 939dc40, release build, run as root on a 4-core Intel Xeon @ 2.10 GHz VM (kernel 6.18), loopback. 2026-11-07.

**Method.** I used the bench tool in a scratch worktree with three env knobs added there only: stub-backend body size, client concurrency, and a dump of utime/stime and the raw `strace -c -f` summary. Each cell is 2 runs × 8 s, closed loop. I also sampled per-thread CPU from `/proc/<pid>/task/*/stat`, and a Python microbenchmark (blocking TCP loopback relay, `RUSAGE_THREAD` sys time) compared read/write against `splice`. `perf` is not installed, so this used strace and /proc instead.

## 1. Proxied responses (keep-alive client, pooled backend connection, 8 clients)

| Body | req/s (saturated) | CPU µs/req | user / sys | syscalls/req |
|---|---|---|---|---|
| 1 KiB | 20 300 | 49 | 27 % / 73 % | 13.5 |
| 64 KiB | 8 000 | 124 | 19 % / 81 % | 38.5 |
| 1 MiB | 700 | 1 430 (runs 1 280–1 510) | 13 % / 87 % | 417 |

Syscalls per request, by call (strace pass):

| Body | read | sendto | epoll_ctl | epoll_wait | other |
|---|---|---|---|---|---|
| 1 KiB | 3.0 | 3.0 | 5.0 | 0.5 | 2 (log write, EAGAIN recvfrom) |
| 64 KiB | 7.0 | 7.0 | 21.0 | 1.5 | 2 |
| 1 MiB | 67.6 | 67.6 | **263.5** | 16.8 | 2 |

How the body moves today: a 16 KiB upstream buffer (`UPSTREAM_RECV_MIN`) is filled, drained and refilled. Each 16 KiB chunk costs 1 read, 1 sendto and about 4 `epoll_ctl` interest changes. The loop thread is at 100 % of one core (13 % user, 87 % sys) in the 1 MiB case.

Where the 1 MiB request's ~1.43 ms goes:
- **read + sendto (the TCP path, copy included): about 0.67 ms per MiB.** This is the microbenchmark's sys time for a 16 KiB-chunk relay, about 55 % of the total. Most of it is TCP stack and loopback delivery, not copying.
- **The copy itself is at most about 0.1 ms per MiB (about 7 %).** One 1 MiB memcpy takes 50 µs here, and the body is copied twice through userspace (in and out).
- **epoll_ctl and epoll_wait churn: about 0.1–0.15 ms (7–10 %).** That is 263 `epoll_ctl` calls at about 0.3–0.5 µs each.
- The rest is user time (13 %) and loop overhead.

What splice could save (microbenchmark: 2 GiB relayed, sys µs per MiB, two runs each):

| Relay | Chunk | sys µs/MiB | syscalls/MiB |
|---|---|---|---|
| read/write | 16 KiB (today) | 667 / 701 | 128 |
| read/write | 64 KiB | 556 / 578 | 32 |
| splice ×2 | 64 KiB pipe | 550 / 591 | 32 |
| read/write | 1 MiB | 414 / 407 | 2.4 |
| splice ×2 | 1 MiB pipe (F_SETPIPE_SZ) | 437 / 405 | 2.4 |

- **Copy elimination:** at the same chunk size, splice saves nothing measurable on this kernel (within ±5 %). The theoretical ceiling is the ~0.1 ms/MiB of copying.
- **Syscall count:** splice changes "read + write per 16 KiB" into "splice ×2 per 64 KiB pipe". It wins only through the **larger chunk**. A plain 64 KiB buffer gives the same gain (−17 % sys, a quarter of the calls) without a pipe, new syscalls or a contract change.
- **Fewer chunks also mean fewer `epoll_ctl` calls**, today about 4 per chunk.

## 2. Static small file at high concurrency (1 KiB, keep-alive)

| Clients | req/s | CPU µs/req | Loop thread CPU |
|---|---|---|---|
| 1 | 8 700 | 90 | — |
| 8 | 19 800 | 61 | ≈ 100 % |
| 64 | 19 000 | 63 | 99 % (28 % user / 71 % sys) |
| 256 | 18 200 | 65 | 99 % (28 % user / 71 % sys) |

- The machine has 4 cores and stayed about 60 % idle overall, so the client was not the limit.
- **The single loop thread saturates one core at about 18–20 k req/s.**
- The 4 `disk-*` worker threads use about 4–5 % each.
- Syscalls per request are 18.5. Most of the futex count is the workers' blocking waits, not CPU.

## 3. At the owner's load (50 req/s)

| Traffic | CPU µs/req | Share of one core at 50 req/s |
|---|---|---|
| static-small | 60–90 | **0.3–0.45 %** |
| proxy-small (1 KiB) | 49 | **0.25 %** |
| proxy 64 KiB | 124 | 0.6 % |
| proxy 1 MiB | 1 430 | **7 %** (if all 50 req/s were 1 MiB proxied) |

- These per-request costs are measured at saturation. At 50 req/s, epoll batching is lost, so the real cost is closer to the 1-client figure (about 1.5×). That is still under 1 % of a core for small requests.
- Headroom on one core: about **370×** for static-small.
- A 1 Gbit/s VPS link carries about 113 MiB/s, which caps 1 MiB responses at about 113 req/s. At that rate the server uses about 16 % of one core: **the link runs out before the CPU.**

## Recommendations

- **Task 6, splice: drop.**
  - What it can save: the userspace copy, ≤ 7 % of a large proxied body's CPU, and measured as ≈ 0 here.
  - What it costs: a pipe pair per proxied connection (+2 descriptors), `pipe2`/`splice` in seccomp on every arch, a contract change and a sim model.
  - The part of the gain that is real (fewer, larger chunks) comes more cheaply from a larger body relay buffer, and from fewer `epoll_ctl` re-arms per chunk.
  - Suggested follow-up: fold "64 KiB vs 16 KiB body buffer" into Task 8's buffer-size measurement (NFR-PERF-05). It is a one-constant change against a multi-part feature. Look at the epoll interest churn there too.
- **Task 7, threads: drop (or defer indefinitely).**
  - The owner's goal is the least CPU per request. Threads do not reduce CPU per request; they only add capacity, and they bring shared counters, N listeners and more wake-ups.
  - One loop thread serves about 18–20 k req/s of small static (a slower VPS core: still ≥ 5–10 k). That is two orders of magnitude above 50 req/s; the server uses < 1 % of a core today.
  - Revisit only if a deployment shows the loop thread near 50 % of a core.

## Caveats

- Everything ran over loopback. The receiver's TCP work is partly charged to the sender, which inflates sys time on both paths equally.
- strace inflates the time of cheap calls, so it is used for call counts only.
- The microbenchmark is Python: its user time is meaningless, only sys time is compared.
